# Project Structure Guide

This guide explains what each folder in the repository is for and how the parts connect. It is written for anyone browsing the code for the first time, including our instructor.

> **Current stage:** foundation. The folders, database connection, health check, and CI pipeline are in place. The database tables and module code are added in Phase 1 (see [PLAN.md](PLAN.md), section 8). Empty folders hold a `.gitkeep` file so Git keeps them.

## The big picture

The RCWheels Business Management System connects four business processes through **one shared database**:

```text
 Requisition  ->  Inventory  ->  Purchasing  ->  Delivery / Receiving
 (request items)  (check and     (order from      (receive goods,
                   reserve stock) suppliers)       deliver internally)
```

It is a single **Next.js** app. The pages and the server code live in the same project:

```text
 Browser  ->  Next.js page (src/app)  ->  module service (src/modules)  ->  Drizzle ORM (src/db)  ->  Supabase PostgreSQL
                                     <-  server action (form submit)  <-
```

| Part | Technology | Job |
| --- | --- | --- |
| Pages and UI | Next.js App Router, Tailwind CSS, shadcn/ui | What the user sees |
| Server code | Next.js server actions and services | Business rules, role checks, saving data |
| Database access | Drizzle ORM + postgres.js | Typed tables and queries |
| Database, login, files | Supabase (PostgreSQL, Auth, Storage) | Stores everything |
| Validation | Zod | Checks every form input on the server |
| Tests | Vitest | Automated checks |
| Hosting | Vercel | Runs the app online |

## Inside one module

Every module has the same folders. Each folder is one **layer**, and each layer has one job. Using `requisition/` as the example:

```text
modules/requisition/
├── index.ts         # The module's "front door". Other modules may only use what this file exports (services and types).
├── components/      # UI for this process: the requisition form, the request table, the status badge
├── actions/         # Server actions: what runs when a form is submitted. Checks the user and role, validates input, calls a service.
├── services/        # Business rules: for example "only a manager can approve" or "reserve stock when approved"
├── repositories/    # Database queries with Drizzle. No rules here, only reading and writing rows.
├── schemas/         # Zod rules for form input (required fields, positive quantities, valid dates)
└── types/           # TypeScript types shared inside the module
```

| Layer | Does | Does not |
| --- | --- | --- |
| `app/` page | Loads data through a service and shows it | Hold business rules |
| `components/` | Forms, tables, buttons | Touch the database |
| `actions/` | Gets the logged-in user, checks the role, validates input, calls one service | Query the database directly |
| `services/` | Business rules and status changes, in one database transaction per business event | Trust a user ID, role, or stock number sent by the browser |
| `repositories/` | Drizzle queries only | Contain rules or call other modules |
| `schemas/` | Zod schemas for forms and action input | Define database tables (those live in `src/db/schema/`) |

### Rules that keep the modules clean

1. Modules only talk to each other through `index.ts`, and only to services.
2. Modules depend in one direction, lowest first: **core -> inventory -> requisition -> purchasing -> delivery**. A module may use modules to its left, never to its right. This prevents circular dependencies.
3. Only the inventory stock service may change stock balances. Every other module asks it to. This keeps one reliable stock ledger instead of four separate records.
4. Table definitions live in `src/db/schema/`, not inside the modules, so the whole database can be read in one place.

## Follow one action: approving a requisition (planned)

This is how the flow will work once Phase 1 code is added:

1. A manager opens the requisition page in `src/app/` and clicks **Approve**.
2. A server action in `modules/requisition/actions/` gets the logged-in user, checks the manager role, and validates the input with a Zod schema from `schemas/`.
3. The action calls the requisition service in `services/`, which checks the requisition is still pending.
4. Inside one database transaction, the service updates the status through `repositories/` and asks the inventory module (through `modules/inventory/index.ts`) to reserve the stock.
5. If any step fails, the whole transaction is rolled back, so stock and status never disagree.
6. The page refreshes and the approved request appears in the Inventory queue.

## Commands

| Command | What it does |
| --- | --- |
| `npm run dev` | Start the app at `http://localhost:3000` |
| `npm run lint` | Check code style |
| `npm run test:run` | Run the tests once |
| `npm run build` | Build for production (also checks TypeScript) |
| `npm run db:generate` | Create a migration from changes in `src/db/schema/` |
| `npm run db:migrate` | Apply migrations to the database in `DATABASE_URL` |
